The following is a detailed technical specification for a distributed task scheduling system. It covers the architecture, the work unit schema, the state machine for task lifecycle, the failure recovery procedures, and the integration points with the model orchestrator service.

The scheduler maintains a persistent work unit file for each delegated task. Each work unit is a JSON document with the following fields: id, a unique identifier for the task; requester, the name of the agent that created the work unit; assignee, the name of the agent or model expected to complete it; status, one of pending, in_progress, done, or failed; brief, a natural language description of the work; constraints, a list of hard constraints the assignee must respect; output_format, one of code, text, analysis, or design; result, populated by the assignee upon completion; result_format, the format of the result; notes, free-form annotations; completed, a boolean flag; and swap_id, the identifier of the model swap that activated this work unit.

The lifecycle of a work unit proceeds in six steps. First, the mastermind creates the work unit and writes it to disk. Second, the orchestrator performs a model swap with context, ensuring the target model has the necessary background information. Third, the assignee reads the work unit from the shared mount. Fourth, the assignee performs the work and writes the result back. Fifth, the orchestrator swaps back to the previous model. Sixth, the mastermind harvests the result and incorporates it into the larger workflow.

Failure recovery follows strict rules. If any phase of the swap fails, the previous model is restored before any new work begins. The swap history log records every transition with timestamps and outcomes. A preflight check verifies GPU memory availability before any stop operation. The watchdog service monitors the gateway and restarts it if it becomes unresponsive.

The system is designed around a single stable port. Whichever model is active serves on port 8020, so the gateway never needs to change its configuration. The swap manager runs on port 8022 and is the only component allowed to start or stop model containers. Containers are pre-created and are never removed; the remove_container function is a no-op by policy.

Context handoff is the hardest problem in the system. When a model is swapped out, its conversation context must be preserved in a way that the incoming model can resume from. The current approach snapshots the session state to a JSON file before stopping the container, and injects a summary of the recent conversation into the system prompt of the incoming model. This is lossy, and the reliability plan identifies it as the main source of context leaks.

The model matrix is a registry of available models with their paths, GPU requirements, context window sizes, capabilities, and load costs. The orchestrator consults this matrix before every delegation decision. A model marked as disabled cannot be selected, and a model whose VRAM requirement exceeds the available GPU memory is excluded from consideration.

The work unit protocol was designed to support batch processing. A batch is a list of work units with priorities, and the orchestrator processes them in order, swapping models only when the assignee changes. This minimizes the number of swaps, which is the most expensive operation in the system, costing on the order of minutes per swap.

The reliability plan, written after four weeks of instability, identified the root causes of the problems. The first was trying to build everything at once, which led to whack-a-mole debugging. The second was coupling the master identity to a specific model binary, which broke when the model was replaced. The third was the lack of a deterministic audit trail for model transitions. The plan prescribes a six-phase approach: swap reliability, context handoff, integration, model matrix, specialized models, and cross-model communication.

The gateway watchdog runs as a separate service on port 8023. It polls the gateway health endpoint and restarts the gateway if it fails three consecutive checks. The watchdog is the only component allowed to restart the gateway; the orchestrator never touches it directly. This separation of duties is a core constraint of the architecture.

The shared volume is mounted at /shared inside the orchestrator container and at /home/gru/.openclaw/workspace/multi-model/shared on the host. All state files, work units, and logs live under this mount, so they survive container restarts. The models volume is mounted read-only from the host model cache, and no model is ever written to or modified by the orchestrator.

The inter-model protocol defines how work units are passed between models of different sizes and capabilities. A small model may create a work unit that requires a large model to execute, and vice versa. The protocol ensures that the assignee has the necessary context, tools, and permissions to complete the work, and that the result is validated before it is returned to the requester.

This document is a draft for review. The architecture has been validated in production for the image generation pipeline, but the LLM orchestration layer remains experimental. The next milestone is a stable MVP that can run a full delegation cycle without manual intervention, from work unit creation to result harvest, with the model swap fully automated and auditable.

The performance characteristics of the system are dominated by the swap time, which includes stopping the previous container, waiting for GPU memory to be freed, starting the new container, and waiting for the model to pass its health check. For a 27 billion parameter model, this process takes between sixty and ninety seconds. The work itself, once the model is loaded, is typically much faster than the swap.

The context window management is critical for long-running tasks. A model with a 131,072 token context window can hold an entire project in memory, but the cost is proportional to the context size. The KV cache for a full context window can consume several gigabytes of GPU memory, leaving less room for the model weights themselves. The system therefore uses a two-slot configuration where the orchestrator slot has a large context and the worker slot has a smaller context, balancing memory usage against task capability.

The failure modes of the system are well understood. The most common failure is a GPU memory leak after a container stop, where the driver does not release the memory within the expected timeout. The swap manager handles this by waiting up to thirty seconds for memory to be freed, and if it is not, it triggers a driver reset. The second most common failure is a health check timeout, where the new model fails to respond within the expected window. In this case, the previous model is restored and the swap is marked as failed.

The audit trail is maintained in swap-history.json, which records every swap operation with its phases, timestamps, and outcomes. This log is the primary debugging tool for the system, and it is preserved across restarts. The orchestrator also maintains an active-model.json state file that records the currently active model and whether it was recovered from a failed swap.

The integration with the Telegram bot is a thin layer that translates user messages into orchestrator API calls. The bot maintains no state of its own; all state lives in the orchestrator. When the user asks for a model swap, the bot calls the swap endpoint and reports the result. When the user asks for status, the bot calls the status endpoint and formats the response.

The security model is minimal, as the system runs on a trusted local network. The orchestrator binds to localhost only, and the Telegram bot uses a token for authentication. There is no multi-user support, and no authorization model beyond the bot token. The shared volume is accessible to any process running as the host user, which is acceptable for a single-user system.

The future roadmap includes support for multiple GPUs, where different models can run concurrently on different cards. This would eliminate the swap entirely for the common case of a large model and a small model working in parallel. The 780M integrated GPU is the target for the small model, running on Vulkan, while the 3090 continues to serve the large model on CUDA.

The current limitation is that the Vulkan implementation of the llama.cpp backend is less optimized than the CUDA implementation, and the integrated GPU shares system memory with the CPU. As a result, the small model runs at a fraction of the speed of the large model, but it runs concurrently, which is the key benefit. The total system throughput increases because the two models are not competing for the same GPU.

The design principle is that the orchestrator is a stable process that outlives the models it manages. The models are interchangeable resources, and the orchestrator's identity is independent of any specific model. This separation of concerns is what makes the system maintainable, and it is the key lesson from the four weeks of instability that preceded the reliability plan.
